# Сборка и тестирование

Все команды выполняются из `src`:

```sh
make                 # Собрать s21_string.a
make test            # Собрать и запустить тесты Check
make gcov_report     # Запустить тесты с покрытием и создать HTML-отчёты
make sanitize        # Запустить тесты с AddressSanitizer и UBSan
make format-check    # Проверить Google Style без изменения файлов
make format          # Отформатировать библиотеку, заголовок и тесты
make clean           # Удалить результаты сборки и отчёты
```

Нужны компилятор C11, `make`, Check и `pkg-config`. Для отчётов дополнительно
нужны `lcov`, `genhtml` и Python 3; для форматирования — `clang-format`.
Флаги подключения Check берутся из `pkg-config`, поэтому путь Homebrew
не прописывается в Makefile.

На macOS `/usr/bin/gcc` обычно запускает Apple Clang. Makefile распознаёт Clang
и использует `tools/llvm-gcov.sh`, чтобы читать его данные покрытия совместимой
версией `llvm-cov gcov`. Для установленного отдельно GCC можно явно указать
компилятор и соответствующий ему `gcov`:

```sh
make clean
make CC=gcc-15 GCOV_TOOL=gcov-15 test gcov_report
```

Здесь `15` — пример: укажи версию установленного компилятора. Перед сменой
компилятора или флагов сборки выполни `make clean`.

В Alpine 3.20 для сборки тестов и HTML-отчёта нужны:

```sh
apk add --no-cache build-base check-dev pkgconf lcov python3 gzip
```

Для санитайзеров штатному GCC в Alpine не хватает runtime. Можно установить
`clang17` и `compiler-rt`, затем после очистки запустить
`make CC=clang-17 sanitize`. Для проверки стиля нужен `clang-format`.

## Организация

- В `test_main.c` объединяются 20 наборов тестов. Программа возвращает `1`
  при проваленных проверках. Цели `make test` и `make gcov_report` допускают
  этот код и продолжают работу; результаты Check остаются в выводе.
  Ошибки компиляции, аварийное завершение программы и ошибки создания
  отчёта по-прежнему останавливают Makefile. `make sanitize` не изменён.
  Для проверки с исходным кодом завершения запусти `./build/tests`
  после сборки командой `make build/tests`.
- Тесты строковых и побайтовых функций находятся в отдельных файлах.
  `test_sprintf.c` и `test_sscanf.c` проверяют форматы, ширину, точность,
  модификаторы, подавление присваивания, возврат функций и граничные случаи.
- `test_extra.c` проверяет результат и выделение отдельной строки для
  `to_upper`, `to_lower`, `insert` и `trim`; выделенная память освобождается.
- Обычные объекты лежат в `build/obj`, объекты с покрытием — в `build/coverage`,
  объекты с санитайзерами — в `build/sanitize`. Они не смешиваются.
- Библиотека собирается только из `s21_*.c`. Старый ручной `tests_file.c`
  в библиотеку и автоматические тесты не включается.
- Заголовки входят в автоматически создаваемые зависимости `.d`.
  Изменение исходника или заголовка вызывает нужную пересборку.

## Покрытие

`make gcov_report` сначала удаляет старые счётчики и запускает тесты. Затем:

1. `lcov` собирает данные только для исходников библиотеки `s21_*.c`.
   Тесты и системные заголовки не повышают процент покрытия.
2. `genhtml` создаёт основной отчёт `report/index.html`.
3. `tools/check_coverage.py` отдельно проверяет покрытие исполняемых строк
   каждой функции, включая внутренние помощники, и создаёт
   `report/functions.html`.

Если хотя бы у одной функции покрыто меньше 80% исполняемых строк, цель
завершается с ошибкой. Общий процент проекта не заменяет эту проверку.
Покрытие строк не является проверкой всех ветвей и всех возможных входов.

В тестах стандартные функции используются как эталон. Для `memcmp` и
`strncmp` сравнивается знак результата; для буферов — все проверяемые байты,
включая нулевые. Для `sprintf` проверяются возвращаемая длина и результат
с завершающим нулём, для `sscanf` — число присваиваний, значения и позиция `%n`.
На macOS предупреждения об устаревании эталонных функций отключены только
при компиляции тестов, остальные предупреждения остаются ошибками.

Результаты сборки и отчёты исключены из Git. Для сдачи нужны исходники,
тесты, Makefile, скрипты из `tools` и `.clang-format`; архив воспроизводится
командой `make`, а не хранится вместо исходников.

## Проверки округления и `%i`

В `test_rounding.c` отдельно проверяются округление половин к чётному, числа
по обе стороны границы округления, перенос в старший разряд и точность за
пределами хранимых цифр. В `test_scanf_i.c` отдельно проверяются знак,
десятичная/восьмеричная/шестнадцатеричная запись, границы `short`, `int`,
`long`, подавление присваивания, ограничение ширины префикса `0x` и ошибки
сопоставления.

Эти наборы можно запускать независимо от остальных проверок:

```sh
CK_RUN_SUITE=rounding make test
CK_RUN_SUITE=scanf_i make test
CK_RUN_SUITE=rounding make sanitize
CK_RUN_SUITE=scanf_i make sanitize
```

## Результаты расширенного набора (16 октября 2026)

Набор расширен с 45 до 69 тестовых сценариев. Внутри сценариев перебираются
различные значения и форматы. Добавлены проверки `e/E/g/G`, `long double`,
`inf/nan`, указателей, нулевых байтов, восьмеричного и шестнадцатеричного
ввода, символов и строк с шириной, вещественного ввода, подавления
присваивания и `%n` с модификаторами. Результаты сравниваются со стандартной
библиотекой текущей платформы. После расширения внесены согласованные
исправления библиотеки, перечисленные ниже. Makefile при этих исправлениях
не менялся.

| Платформа | Прошло тестов | Покрытие строк библиотеки | Минимум среди 66 функций |
| --- | ---: | ---: | ---: |
| macOS ARM64, Apple Clang 21, Check 0.15.2 | 62/69 | 96,3% (1875/1947) | 81,8% |
| Alpine 3.20.10 ARM64, GCC 13.2.1, musl, Check 0.15.2 | 64/69 | 97,1% (1595/1642) | 88,9% |

Последний повторный прогон Valgrind и покрытия на Linux выполнен в Alpine
ARM64. Ранее функциональные проверки также выполнялись в Alpine x86_64.

В реализации сохранены следующие исправления:

- Поле для `inf` заполняется пробелами даже с флагом `0`.
- Очень малые числа `double` преобразуются с учётом отсутствия неявного
  старшего бита мантиссы; ширина научной записи учитывает три цифры экспоненты.

По просьбе пользователя удалены две платформенные развилки. Нулевой
указатель снова всегда выводится как `(nil)`. Неполное чтение `%3c` снова
считается успешным независимо от платформы. Это вернуло два падающих
сценария на Alpine и один на Mac; таблица выше обновлена после удаления.

Существующие четыре сценария дополнены сравнениями для знаков и флагов
`inf`, ширины поля указателя, положительных и отрицательных субнормальных
чисел в `e/E/g/G/f`, а также пустого, неполного и полного ввода `%3c`
с подавлением присваивания и без него. Проверки `inf` и малых чисел проходят
на обеих платформах. Проверка нулевого указателя падает на обеих, проверка
неполного `%3c` — на Alpine.

Каждая функция, включая помощники, покрыта более чем на 80% на обеих
платформах. Однако это данные запуска с падающими проверками: они не
означают, что функции работают правильно или проект готов к сдаче.
По просьбе пользователя цели `make test` и `make gcov_report` настроены
продолжать работу при коде `1` от программы тестов. Поэтому HTML-отчёт
создаётся и при проваленных проверках. Успешный код завершения этих целей
не подтверждает прохождение тестов: фактический результат указан в строке
Check `Checks / Failures / Errors`. Сама программа тестов по-прежнему
возвращает `1`, если проверки не прошли.

На обеих платформах остаются следующие ошибки:

- `sprintf("%p", NULL)` выводит `(nil)` вместо `0x0` на Mac или `0` в musl.
- `sscanf("inf", "%lf%n", ...)` не распознаёт бесконечность.
- `sscanf("0x1.8p+2", "%lf%n", ...)` читает только первый `0` вместо
  вещественного числа `6`.

Дополнительно на Alpine падают проверки сохранения точности `long double`
в `sprintf` и неполного ввода `%3c`: возвращается успешное присваивание,
а `%n` выполняется, хотя musl останавливает преобразование.
На Mac падают проверки знака
`nan`, незавершённого показателя степени `"1e+"` и две проверки `%2i`
для `"0x1f"`. Последняя ошибка учитывается двумя разными сценариями.

В `s21_sprintf.c` внесены согласованные правки безопасности:

- В `s21_printeger` отрицание минимального числа выполняется в беззнаковом
  типе: `0ULL - (unsigned long long)n`.
- В `s21_prstr` цикл проверяет точность до чтения следующего символа.
  Массив без завершающего нуля можно безопасно передавать с достаточным
  ограничением точности, например `%.3s` для массива из трёх символов.
- В `s21_prgdouble` вместо `char tmp[2048]` выделяется буфер размером
  `P + 16`, где `P` — заданная точность. Проверяется результат `malloc`,
  а после форматирования выполняется `free(tmp)`.

В существующий сценарий общего вещественного формата добавлены пять
сравнений со стандартным sprintf для точности 3000: `g/G`, с флагом `#`
и без него, для обычных, малых и субнормальных чисел. Число сценариев
осталось 69.

Valgrind 3.23.0 в Alpine ARM64 после исправления буфера:

- Полный набор: 0 ошибок памяти, 0 байт в 0 блоках на выходе;
  19048 выделений и столько же освобождений. Пять сравнений с эталоном
  по-прежнему не проходят, поэтому программа тестов возвращает 1.
- Отдельный ранее аварийный `%#.3000g`: сравнение с эталоном успешно,
  0 ошибок памяти, 3 выделения и 3 освобождения, утечек нет.

На Mac этот отдельный пример также проходит с ASan/UBSan. Cppcheck 2.21
в exhaustive-режиме не добавил новых диагностик: 0 error, 9 warning,
90 style и 1 information; сообщений об утечках и выходах за границы нет.

Две существующие проверки — границ целых чисел и строки с ограниченной
точностью — ранее отдельно прошли с AddressSanitizer и UBSan. Четыре
сценария до удаления платформенных развилок также отдельно прошли с этими
санитайзерами на Mac. Последний полный запуск 69 сценариев на Mac завершился
без сообщений санитайзеров, но `make sanitize` возвращает ошибку из-за
оставшихся 7 сравнений с эталоном.
Стиль проверен командой `make format-check`.

Перед сдачей нужны исправления обнаруженных ошибок и повторный успешный
запуск тестов с покрытием. Не следует удалять эти проверки ради успешного
кода завершения.
